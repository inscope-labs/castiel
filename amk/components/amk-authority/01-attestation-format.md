# 01-attestation-format.md

**File:** `01-attestation-format.md`
**Scope:** Attestation structure, serialization, signing keys, metadata, validity rules.
**Reference prefix:** `ATA-01`

---

## ATA-01:01 Structure

- A role attestation is a JSON object (RFC 8259, UTF-8). It MUST contain the following fields:
  - `issuer`: the Authority's identifier (an HTTPS URL).
  - `kid`: the identifier of the signing key (`ATA-01:07`).
  - `subject_public_key`: the session public key.
  - `role`: the role string.
  - `session_handle`: the session handle.
  - `epoch`: the epoch number (non-negative integer).
  - `valid_from`: the start of the validity window.
  - `valid_to`: the end of the validity window.
  - `nonce`: a unique nonce for this attestation. It is also the attestation's identifier in revocation lists (`ATA-04`).
  - `signature`: the Authority's signature over the canonical serialization.
- Binary values in every Authority structure are base64url without padding (RFC 4648, section 5). Timestamps are RFC 3339 in UTC with a `Z` suffix.
- No other fields are permitted unless a profile defines them. Verifiers MUST reject attestations that contain undefined fields.

## ATA-01:02 Canonical Serialization

- The signature MUST be computed over the JSON Canonicalization Scheme (JCS, RFC 8785) serialization of the attestation object without the `signature` field.
- All numeric fields are integers.

## ATA-01:03 Validity Window

- `valid_from` MUST be less than or equal to `valid_to`.
- `valid_from` MUST NOT precede the start of the epoch, and `valid_to` MUST NOT exceed the end of the epoch plus the grace window `G` (`DV-ATA-01`). [INV-ATA-06]
- The window length MUST NOT exceed the maximum validity window (`DV-ATA-03`).
- Epoch start and end MUST come from the controller's session record (`ATA-02:02`), never from the requester.
- The Authority MUST refuse to issue an attestation with an invalid window.

## ATA-01:04 Nonce

- The `nonce` field MUST be unique per attestation.
- The nonce MUST be generated by the Authority using a cryptographically secure random source.
- The nonce length MUST be at least 128 bits.

## ATA-01:05 Signature

- The mandatory-to-implement signature algorithm is Ed25519 (RFC 8032).
- Another algorithm MAY be used only if the signed metadata lists it for the signing key and the profile permits it.
- The algorithm is taken from the metadata entry for the attestation's `kid`, never from the attestation itself.
- Clients MUST reject attestations whose key has an unknown or unsupported algorithm.

## ATA-01:07 Signing Keys and Metadata

- The Authority MUST publish a signed metadata document at `/.well-known/amk-authority` on its issuer origin (RFC 8615), over HTTPS, as `application/json`.
- The document MUST contain: `issuer`, `metadata_version` (integer that never decreases), `published_at`, `profile` (`basic`, `standard` or `high`), `root_kid`, `signing_keys`, `revocation_list_url`, `signature`.
- It MUST also contain `revocation_status_url` under High, MAY contain it under Standard, and MUST contain `client_authentication` and `evidence` where `ATA-02:05` and `ATA-06:04` require them.
- Each entry of `signing_keys` MUST contain `kid`, `alg`, `public_key`, `not_before`, `not_after` and `status`. `status` is `active`, `retired` or `revoked`.
- `kid` is the base64url SHA-256 JWK Thumbprint (RFC 7638, OKP key members as in RFC 8037) of the public key.
- The Authority MUST have one root key. The root key signs metadata documents only (JCS, `ATA-01:02`) and never attestations or revocation lists.
- Clients pin the root public key (and `issuer`) out of band at deployment. A client MAY pin more than one root key during a root rotation. Root rotation is out-of-band re-pinning.
- The Authority signs attestations and revocation lists only with a key whose `status` is `active`. A `retired` key signs nothing new; attestations it signed stay valid until their own `valid_to`. A `revoked` key's signatures MUST be rejected.
- Rotation: publish the new key as `active`, then mark the old key `retired` at the switch. The old key MAY be removed once every attestation it signed has expired. A compromised key is marked `revoked`.
- Clients MUST verify the metadata signature with a pinned root key, MUST reject a `metadata_version` lower than the last one they saw, and MUST reject an attestation whose `kid` is absent from the metadata or whose key status is `revoked`.
- Each `kid` in `signing_keys` MUST be unique, and MUST equal the thumbprint of its `public_key`. Clients MUST reject a metadata document that lists a `kid` more than once or whose `kid` does not match its key, and MUST NOT guess between ambiguous keys.
- Clients MUST refresh metadata when their cached copy is older than `DV-ATA-08`, and MUST reject attestations when that refresh fails and the cached copy is still older than `DV-ATA-08`.
- Servers SHOULD set `Cache-Control: max-age` no larger than `DV-ATA-08` (RFC 9111).

## ATA-01:08 Summary

- An attestation is a JCS-canonical JSON object signed with Ed25519 by a key listed in signed metadata. Its window lies inside the controller-defined epoch plus the grace window. Keys, profile, and endpoints are published in signed metadata verified against a pinned root key.
