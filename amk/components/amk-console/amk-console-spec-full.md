## Holistic System Overview

The amk-console is the sole seat of human operator authority. It is a self-contained component that communicates with external entities through signed envelopes; the sole exception is delivery of the session handoff to a Host AI (CNS-3:21). It has no knowledge of the internal behaviour of the controller, Host AI, runtimes, gateways, or any other counterpart; it only knows the envelope schemas, the cryptographic verification rules it must apply, and the sequencing obligations defined in this specification.

The console is trusted to capture and transmit authenticated operator intent. It is untrusted for enforcement: every action is submitted as a signed envelope that the receiving party alone enforces. Mutual verification is mandatory.

All external interactions are envelope-based, except handoff delivery (CNS-3:21). Local presentation, user-interface design, notification rendering, first-run experience, and operator-load timing are outside the scope of this specification and belong in an implementation guide.

The specification is language-agnostic. Implementations may be written in any language that can satisfy the cryptographic and sequencing requirements of the claimed operational profile.

Three operational profiles—Basic, Standard, and High—govern privacy, security, and implementation complexity. Higher profiles subsume all requirements of lower profiles.

Normative requirements live in the module files listed below.

## Foundations — Terms, Role, Trust & Invariants

**File number:** 1  
**Overview.**  
This module defines the core terminology, the console’s role as the sole human representation of the operator, the trust boundary, and the absolute invariants. All subsequent modules presuppose these definitions. The console is treated as a self-contained component that interacts solely via envelopes.

---

### Terms

| Term | Meaning |
|---|---|
| Console | The component defined by this specification. |
| Controller | External black-box component that receives console envelopes and performs enforcement. |
| Operator | The human whose authenticated intent the console represents. |
| Envelope | A structured, signed, nonced, sequenced message that is the sole external communication unit. |
| Session | A unit of work mediated by the controller and started by a console envelope. |
| Handoff | An expiring credential returned by the controller that allows a session to begin. |
| Work order | A task statement carrying its own quota and constraints. |
| Pre-authorization envelope | A reusable, operator-signed advance approval for a named scope. |
| Validation gate | A deterministic check the console MUST apply to any controller-proposed surface before acceptance. |
| Role / Runtime | External entities registered or included via envelopes; treated as black boxes. |
| Attestation / Signature | Cryptographic proof of origin and integrity; verification rules are defined in this specification. |

---

### Role

- **CNS-1:1** The console is the sole seat of operator authority and the sole interface through which authenticated human intent enters the system.
- **CNS-1:2** The controller has no independent notion of an operator; the console’s cryptographic identity is how the operator is present.
- **CNS-1:3** The console submits signed envelopes; the controller (or other receiving party) enforces.

### Trust Boundary

- **CNS-1:4** The console is trusted for capturing and transmitting authenticated operator intent.
- **CNS-1:5** The console is untrusted for enforcement.
- **CNS-1:6** The console MUST verify every signature and response it receives from external parties.
- **CNS-1:7** External parties MUST be able to verify every signature the console emits.
- **CNS-1:8** The console MUST NOT rely on the internal behaviour of any counterpart beyond the envelope contract.

### Invariants

- **CNS-1:9** No implicit authority. Every action that affects system state is an explicit signed envelope.
- **CNS-1:10** The console is the sole human representation.
- **CNS-1:11** Enforcement authority lies outside the console.
- **CNS-1:12** A failed validation gate is never overridden.
- **CNS-1:13** Long-term private keys never leave the console’s protected key store.
- **CNS-1:14** The console never accepts an envelope whose signature or freshness checks fail.
- **CNS-1:15** All external communication occurs through envelopes defined in this specification, subject to the exception in CNS-3:21.

**CNS-1:16** An implementation that violates any invariant listed above is non-conformant.

## Keys and Authentication

**File number:** 2  
**Overview.**  
This module defines the abstract key hierarchy and the authentication/confirmation requirements. Concrete protection strength is governed by the operational profile (see file 7). The specification remains language- and platform-agnostic.

---

### Key Hierarchy

- **CNS-2:1** The console MUST maintain a console signing key used to sign all envelopes that express operator intent.
- **CNS-2:2** The console MAY maintain a distinct map/surface key used exclusively to sign surface-acceptance envelopes.
- **CNS-2:3** The console MUST maintain pinned verification keys for the controller and any other parties whose envelopes it accepts. These keys are obtained through a trusted bootstrap mechanism.
- **CNS-2:4** Under the Standard and High profiles, all private keys MUST be non-exportable.
- **CNS-2:5** Under the Basic profile, software-protected keys are permitted.

### Confirmation Policy

- **CNS-2:6** Certain envelope types require proof that a human operator has freshly authorized the action. The strength of that proof is profile-dependent (see file 7).
- **CNS-2:7** High-impact actions (session start, pre-authorization creation or change, key changes, revocation of active sessions) MUST require a fresh confirmation under the Standard and High profiles.
- **CNS-2:8** The Basic profile MAY relax confirmation strength for some actions.
- **CNS-2:9** The precise mechanism of “fresh confirmation” is an implementation concern; the resulting envelope MUST carry evidence that the confirmation occurred according to the claimed profile.

### Profile-Dependent Key Protection

(See file 7 for the full normative table. The following are the core statements.)

- **CNS-2:10** Duplicate of CNS-7:12. The requirement is defined only there.
- **CNS-2:11** Duplicate of CNS-7:17. The requirement is defined only there.

- **CNS-2:12** The console build MUST pin the Release Key fingerprint(s), the list of controller URLs, and the list of Authority URLs. These pins are the root of trust for the administrative channel (CNS-3:19). How the controller signing key and the Authority public key reach the console is not yet defined (see CNS-O-13).

<a id="file-02-envelope-interface"></a>

## Envelope Interface

**File number:** 3  
**Overview.**  
This module defines the sole external communication mechanism of the console: signed envelopes. Every interaction with the controller or any other external party occurs through envelopes. Common fields, sequencing, freshness, and verification rules are specified here.

---

### Common Envelope Rules

- **CNS-3:1** Every envelope MUST contain a unique nonce of at least 128 bits.
- **CNS-3:2** Every envelope MUST contain a timestamp.
- **CNS-3:3** Every envelope MUST contain a monotonic sequence number scoped to the sender identity.
- **CNS-3:4** Every envelope MUST contain an explicit type identifier and the sender’s identity.
- **CNS-3:5** Every envelope MUST be signed over its canonical serialization by the sender’s appropriate key.
- **CNS-3:6** The console MUST reject any envelope whose signature fails verification against a pinned public key.
- **CNS-3:7** The console MUST reject any envelope whose timestamp falls outside the allowed skew window.
- **CNS-3:8** The console MUST reject any envelope whose nonce has been seen before.
- **CNS-3:9** Under the Standard and High profiles the console MUST reject any envelope whose sequence number is not strictly greater than the last accepted sequence number from that sender. The Basic profile MAY use weaker sequencing.
- **CNS-3:10** The console MUST produce envelopes that satisfy the same rules so that external parties can apply identical verification.

### Envelope Catalogue

- **CNS-3:11** The following envelope types are defined by this specification. Additional types may be added by companion specifications provided they obey the common rules above.

| Type | Direction | Purpose |
|---|---|---|
| `SessionStart` | Console → Controller | Initiate a new session |
| `ExecutionProfile` | Console → Controller | Supply work orders, runtime selections, context |
| `SurfaceProposal` | Controller → Console | Proposed surface for validation |
| `SurfaceAcceptance` / `SurfaceRejection` | Console → Controller | Result of validation gates |
| `Handoff` | Controller → Console | Session start credential |
| `HandoffDelivery` / `HandoffReceipt` | Console ↔ external | Delivery and acknowledgement of handoff |
| `RuntimeInclusionDecision` | Console → Controller | Approve or deny inclusion of an already-registered runtime in a running session (see CNS-O-10) |
| `WorkOrder` / `WorkOrderUpdate` | Console → Controller | Create, extend, renew, cancel |
| `PreAuthorization` | Console → Controller | Create, change, or revoke a pre-authorization |
| `Revocation` | Console → Controller | Immediate revocation of session, runtime, or pre-auth |
| `StatusQuery` / `StatusResponse` | Console ↔ Controller | Request and receive state or audit information |
| `Notification` | Controller → Console | Pending decision or event |
| `ValidatorEvidence` | Console → Controller | Optional session-validator observation |
| `Genesis` | Console → Controller | Console-signed anchor that locks console, Host AI, controller and gateways into one session; the genesis value MUST be 0 at handoff (see CNS-O-09) |
| `TurnReceipt` | Console → Controller | Console-signed receipt for a turn (see CNS-O-09) |

- **CNS-3:12** All of the above are ordinary envelopes subject to the common rules. No transport other than the channels defined in CNS-3:19 and the delivery exception in CNS-3:21 is permitted for control-plane actions.

### Sequencing and Sessions

- **CNS-3:13** Duplicate of CNS-3:3. The requirement is defined only there.
- **CNS-3:14** Session-related envelopes carry a session handle once one has been allocated.
- **CNS-3:15** The console MUST maintain sufficient state to enforce monotonicity and replay protection for the lifetime required by the claimed profile.

### Contract Version and TTL

- **CNS-3:16** Every envelope MUST contain a `contract_version` equal to the suite major.minor to which the sender conforms (`amk-ssot.md`, SSOT-1:3).
- **CNS-3:17** Every envelope MUST contain a `ttl` after which the envelope MUST be rejected.
- **CNS-3:18** The console MUST reject any envelope whose `contract_version` it does not support or whose `ttl` has expired. It MUST NOT silently downgrade.

### Channels

- **CNS-3:19** The console and the controller communicate over two distinct channels. The **administrative channel** is direct, its trust is rooted in the Release Key, and it is required to initiate a session. The **session channel** carries all session-based communication through the session router; envelopes are router payloads.
- **CNS-3:20** `SessionStart` is sent on the administrative channel. Once a session handle has been allocated, every session-related envelope MUST use the session channel. The assignment of the remaining envelope types to channels is not yet defined (see CNS-O-08).
- **CNS-3:21** Delivery of the handoff to a Host AI by manual, loopback or gateway means is the only permitted transport that is not an envelope exchange.
- **CNS-3:22** The encapsulation of envelopes as router payloads is defined by the session-router specification (see CNS-O-08).

<a id="file-03-session-lifecycle"></a>

## Session Lifecycle

**File number:** 4  
**Overview.**  
This module defines the envelope exchanges that constitute session start, handoff handling, and mid-session runtime inclusion or removal. All steps are expressed solely as envelope types and verification obligations.

---

### Session Start

- **CNS-4:1** The console initiates a session by emitting a `SessionStart` envelope (and any required follow-on `ExecutionProfile` or work-order envelopes).
- **CNS-4:2** The controller is expected to respond with a session handle and a `SurfaceProposal` envelope.
- **CNS-4:3** The console MUST apply validation gates (file 6) before emitting a `SurfaceAcceptance` envelope.
- **CNS-4:4** On validation failure the console MUST emit a `SurfaceRejection` envelope.
- **CNS-4:5** After acceptance the controller is expected to return a `Handoff` envelope.
- **CNS-4:6** A covering pre-authorization MAY allow the console to emit `SurfaceAcceptance` without additional operator confirmation, subject to profile rules (file 7).
- **CNS-4:7** The operator MAY have multiple concurrent sessions; each is identified by its session handle.

### Handoff

- **CNS-4:8** The `Handoff` is an expiring credential. The console treats it as opaque data.
- **CNS-4:9** Under the Standard and High profiles the console MUST NOT log the handoff value in clear text.
- **CNS-4:10** The console MAY emit a `HandoffDelivery` or `HandoffReceipt` envelope according to the delivery path.

### Mid-Session Runtime Inclusion / Removal

- **CNS-4:11** RETIRED. Replaced by CNS-4:16.
- **CNS-4:12** The outcome of the inclusion workflow is communicated to the controller by a `RuntimeInclusionDecision` envelope (accept or reject). Whether this is a distinct envelope type is open (see CNS-O-10).
- **CNS-4:13** Under a covering pre-authorization the decision MAY be emitted automatically according to profile rules.
- **CNS-4:14** Inclusion does not require a new handoff; the existing session handle continues.
- **CNS-4:15** The console MAY emit a `Revocation` envelope targeting a runtime within a session.
- **CNS-4:16** Mid-session inclusion of an already-registered runtime is requested by the operator or by the Host AI. Handling the request is an exclusive console workflow; no `RuntimeInclusionRequest` envelope exists.

<a id="file-04-runtimes-work-preauth"></a>

## Runtimes, Work Orders, Pre-Authorization & Auto Assist

**File number:** 5  
**Overview.**  
This module defines the envelope contracts for runtime registration, work-order management, pre-authorization envelopes, and Auto Assist behaviour. All interactions are envelope-based; counterparts are treated as black boxes.

---

### Runtime Registration

- **CNS-5:1** RETIRED. Replaced by CNS-5:13.
- **CNS-5:2** The console does not interpret the internal semantics of a runtime beyond the fields required by the envelope schema.

### Work Orders

- **CNS-5:3** Work orders are created, extended, renewed, or cancelled by emitting the corresponding `WorkOrder` or `WorkOrderUpdate` envelopes.
- **CNS-5:4** Each work order carries its own quota and constraint fields.
- **CNS-5:5** The console treats the controller’s acceptance or rejection as authoritative.

### Pre-Authorization Envelopes

- **CNS-5:6** A pre-authorization is a reusable, console-signed envelope that authorizes a named scope up to stated limits (expiry, quota, level cap, runtime version, etc.).
- **CNS-5:7** Creation or modification of a pre-authorization MUST require a fresh confirmation under the Standard and High profiles.
- **CNS-5:8** The console deposits the signed pre-authorization with the controller via a `PreAuthorization` envelope.
- **CNS-5:9** A covering pre-authorization allows the console to emit certain acceptance envelopes without additional confirmation, subject to the limits recorded in the pre-authorization.
- **CNS-5:10** Revocation of a pre-authorization is performed by emitting a `Revocation` envelope.

### Auto Assist

- **CNS-5:11** Auto Assist is expressed as a policy flag carried in session-related envelopes or as a standing pre-authorization scope.
- **CNS-5:12** When the console is unreachable, continuation of a session is governed solely by the limits of an applicable pre-authorization and the information supplied by the controller.
- **CNS-5:13** Runtime registration is an exclusive console workflow. It is console-local and involves no envelope.

<a id="file-05-validation-revocation"></a>

## Validation, State Rules, Revocation & Recovery

**File number:** 6  
**Overview.**  
This module defines the validation obligations the console must discharge before accepting a surface, the rules for relying on external state, the revocation interface, and the recovery posture. All behaviour is expressed as envelope verification and emission rules.

---

### Validation Gates

- **CNS-6:1** Before emitting a `SurfaceAcceptance` envelope the console MUST apply every validation gate defined by the referenced gate set.
- **CNS-6:2** A failed gate MUST produce a `SurfaceRejection` envelope.
- **CNS-6:3** A failed gate MUST NOT be overridden by the operator or by a pre-authorization (see CNS-1:12).
- **CNS-6:4** The console MUST record the gate-set version in the acceptance or rejection envelope.

### State Rules

- **CNS-6:5** The console treats the controller as the sole authority for session state.
- **CNS-6:6** Any locally cached state MUST be treated as unverified until confirmed by a freshly verified envelope from the controller.
- **CNS-6:7** Under the Standard and High profiles the console MUST enforce strict freshness and sequencing on all state-bearing envelopes.

### Revocation

- **CNS-6:8** The console MAY emit a `Revocation` envelope targeting an entire session, a runtime within a session, or a previously issued pre-authorization.
- **CNS-6:9** When the controller is unreachable the console relies on the natural expiry of credentials and pre-authorizations as the backstop.

### Recovery

- **CNS-6:10** Recovery of console identity and key material after loss or compromise is profile-dependent and remains an open item.
- **CNS-6:11** The Basic profile MAY permit simple re-keying; Standard and High profiles require a defined recovery protocol that preserves the non-exportable and hardware-backed properties of the keys.

## Operational Profiles

**File number:** 7  
**Overview.**  
This module defines the three operational profiles—Basic, Standard, and High—that govern privacy, security, and implementation complexity. An implementation MUST declare exactly one profile. Higher profiles subsume all requirements of lower profiles.

---

### Common Rules

- **CNS-7:1** Every conformant implementation MUST declare exactly one profile: `basic`, `standard`, or `high`.
- **CNS-7:2** The declared profile MUST be discoverable through a status or capability envelope.
- **CNS-7:3** An implementation claiming `standard` MUST satisfy every Basic requirement in addition to the Standard obligations.
- **CNS-7:4** An implementation claiming `high` MUST satisfy every Basic and Standard requirement in addition to the High obligations.
- **CNS-7:5** The invariants defined in file 1 apply at every profile.

---

### Basic Profile

**Target:** Hobbyists, educational use, rapid prototypes, early experimentation.

- **CNS-7:6** Software-protected keys are permitted.
- **CNS-7:7** Soft isolation is acceptable.
- **CNS-7:8** Sequencing and replay protection MAY use simplified mechanisms.
- **CNS-7:9** Fresh confirmation MAY be relaxed for some high-impact actions.
- **CNS-7:10** Minimal audit retention is acceptable.
- **CNS-7:11** The Basic profile is suitable for any programming language that can perform the required public-key operations and maintain basic monotonic state.

### Standard Profile

**Target:** Production services and professional deployments.

- **CNS-7:12** Private keys MUST be non-exportable and protected by an OS keystore or equivalent.
- **CNS-7:13** Process or container isolation between the console and any less-trusted components is required.
- **CNS-7:14** Full envelope sequencing, freshness, and replay protection are mandatory.
- **CNS-7:15** Fresh confirmation is required for session start, pre-authorization creation/change, key changes, and active-session revocation.
- **CNS-7:16** A complete audit trail of emitted and accepted envelopes MUST be maintained for the retention period defined by policy.

### High Profile

**Target:** Enterprise, regulated, and high-assurance environments.

- **CNS-7:17** Private keys MUST be protected by an HSM, secure element, or TEE and MUST NOT exist in ordinary process memory in clear form.
- **CNS-7:18** Strong isolation (TEE or equivalent hardware security domain) is required.
- **CNS-7:19** Measured boot / remote attestation of the console’s key environment SHOULD be supported.
- **CNS-7:20** Strict fresh confirmation for all high-impact actions is required; additional environmental checks may be required.
- **CNS-7:21** The audit trail MUST be protected against tampering (hardware-backed or equivalently strong integrity protection).
- **CNS-7:22** Side-channel resistance and high-assurance coding practices are expected for the security-critical paths.

---

### Profile Summary Table

| Requirement | Basic | Standard | High |
|---|---|---|---|
| Non-exportable keys | SHOULD | MUST | MUST |
| OS keystore / equivalent | MAY | MUST | MUST |
| HSM / TEE / secure element | — | MAY | MUST |
| Keys never in clear process memory | — | SHOULD | MUST |
| Process / container isolation | MAY | MUST | MUST |
| TEE-level isolation | — | — | MUST |
| Full sequencing + replay protection | MAY (simplified) | MUST | MUST |
| Fresh confirmation for high-impact actions | MAY relax | MUST | MUST |
| Tamper-protected audit trail | Minimal | Full | Hardware-protected |
| Remote attestation support | — | — | SHOULD |

### Peer Profile Rule

- **CNS-7:23** The console MUST NOT accept a peer that declares a lower profile than its own unless the operator has explicitly allowed it, and that allowance MUST be audited.

### Migration Notes

- All UI/UX, presentation, operator-load timing, deep-linking, first-run wizards, notification rendering, and platform-specific material has been removed.
- The console is defined solely by its envelope contracts and verification obligations.
- Three operational profiles (Basic / Standard / High) are defined in file 7.
- The specification is language-agnostic.
- Reference IDs now follow the single scheme `CNS-<file>:<rule>`.
- `RuntimeRegistration`, `RuntimeInclusionRequest` and `ClarificationAnswer` envelopes were removed. Runtime registration and inclusion handling are console workflows; `ClarificationAnswer` is discontinued. CNS-4:11 and CNS-5:1 are marked `RETIRED`.
- `Genesis` and `TurnReceipt` envelopes were added to the catalogue. Common envelope fields now include `contract_version` and `ttl`.
- Cross-spec open items are indexed in `specs/core/OPEN-ITEMS.md`.
