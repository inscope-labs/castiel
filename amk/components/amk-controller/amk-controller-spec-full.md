## Holistic System Overview

The amk-controller is the sole authoritative enforcement point, token-issuance engine, and state authority. It holds the complete picture of session and epoch state. Principals are consoles identified by cryptographic keys; the controller has no notion of a human operator.

All control-plane interaction with consoles occurs through signed envelopes. The controller verifies console signatures and envelope validity; it does not rely on the internal implementation of any console. Interactions with Host AI channels (HTSM and any additional channels) and with runtimes are defined by protocol contracts. The controller treats external parties as black boxes beyond the verification and protocol obligations stated in this specification.

The specification is language- and platform-agnostic. An implementation may be written in any language and run on any platform that can satisfy the cryptographic, isolation, durability, and sequencing requirements of the claimed operational profile. Higher profiles (especially High) may exclude languages or platforms that cannot provide the required key protection, isolation, or audit strength.

Three operational profiles—Basic, Standard, and High—govern privacy, security, and implementation complexity. Higher profiles subsume all requirements of lower profiles.

Local presentation, user-interface design, and operator-facing summaries are outside the scope of this specification and belong in an implementation guide.

Normative requirements live in the module files listed below.

## Foundations — Role, Trust, Authority & Invariants

**File number:** 1  
**Overview.**  
This module defines the controller’s role as the sole enforcement and state authority, the trust boundary, the authority model, and the absolute invariants. The specification is language- and platform-agnostic; profile requirements may exclude languages or platforms that cannot meet the stated isolation and key-protection strength.

---

### Role

- **CTR-1:1** The controller is the sole authoritative enforcement point, token-issuance engine, and state authority. It holds the complete picture of state.
- **CTR-1:2** It verifies the Release Manifest, authenticates runtimes, validates request envelopes, builds and serves surface maps, and runs the baseline Host AI channel protocol (HTSM).
- **CTR-1:3** It emits cryptographically signed responses, capability tokens, audit entries, and checkpoints.
- **CTR-1:4** The controller has no notion of a human operator. Its principals are consoles identified by their keys. One controller MAY serve many consoles.

### Trust Boundary

- **CTR-1:5** Trusted: Release Key holders, console keys (for intent), conforming adapters, and the platform on which the controller itself runs (subject to the claimed profile).
- **CTR-1:6** Untrusted: the Host AI, runtimes, unauthenticated parties, and external network data. The console is trusted only for authenticated operator intent.
- **CTR-1:7** The Host AI and prompt layer are entirely untrusted for enforcement or authorization.
- **CTR-1:8** The controller and console do not trust each other blindly: each verifies the other’s signatures and responses.

### Authority Model

- **CTR-1:9** No implicit authority. Authority is never inferred from presence, context, prompt content, or authentication alone.
- **CTR-1:10** Identity authentication, capability authorization, runtime execution, and task completion remain separate.
- **CTR-1:11** Layered policy precedence: immutable invariants, kernel policy, runtime contract, capability policy, task policy, agent request. Deny beats require-confirmation beats allow.
- **CTR-1:12** Risk classes are evaluated; runtime policies MUST NOT weaken kernel boundaries.
- **CTR-1:13** The release policy defines the required items the controller may add to a surface on its own. It MUST NOT add anything else.

### Invariants

- **CTR-1:14** No action occurs without cryptographic verification, valid tokens (where required), and explicit authorization.
- **CTR-1:15** A failed integrity check triggers safe-halt and is never bypassed.
- **CTR-1:16** Fail-closed on any failure condition.
- **CTR-1:17** No silent downgrades of protocol, contract, or capability versions.
- **CTR-1:18** The controller never creates or widens a pre-authorization envelope.
- **CTR-1:19** The Host AI never receives a capability token; it learns only outcomes.
- **CTR-1:20** An implementation that violates any invariant is non-conformant.

## Bootstrap, State Model & Lifecycle

**File number:** 2  
**Overview.**  
This module defines bootstrap from the Release Manifest, the nested state model, and lifecycle transitions. Concrete durable-storage technology is left to the implementation; only the required durability and single-writer properties are normative. Profile strength governs how strongly these properties must be enforced.

---

### Bootstrap

- **CTR-2:1** The controller MUST fetch and verify the Release-signed Release Manifest from the designated bootstrap location against the Release Key fingerprint and anti-rollback epoch rules.
- **CTR-2:2** The Release Manifest MUST identify the HTSM protocol version, a hash of the kernel subtree definition, and the release’s required-items list or its hash.
- **CTR-2:3** Lifecycle state moves through ABSENT → LOADING → VERIFYING → READY.
- **CTR-2:4** On bootstrap failure the controller MUST notify the administrator (out of band) and answer consoles with a standard error code.
- **CTR-2:5** After the Release Manifest verifies, the controller is idle and waits for connections.
- **CTR-2:6** The controller MUST enforce strict bootstrap readiness before accepting any connection or command.

### State Model

- **CTR-2:7** State is nested and scoped. Release and deployment state are global; everything else is scoped to a session, surface, subtree, proposal, or runtime so that one failure does not halt another party.
- **CTR-2:8** Failure conditions include INTEGRITY-FAILED, CONTRACT-FAILED, FAULTED, and SAFE-HALT, with health NORMAL or DEGRADED. BLOCKED and AUTHORIZATION-FAILED are scoped conditions.
- **CTR-2:9** Each session carries an anomaly level (see file 6).
- **CTR-2:10** The controller changes lifecycle only by restricting. Permissive transitions require console authority.
- **CTR-2:11** Duplicate of CTR-1:16. The requirement is defined only there.

### Durability and Concurrency

- **CTR-2:12** Session and epoch state MUST be held in durable storage that supports point-in-time recovery (or an equivalent durability guarantee required by the claimed profile).
- **CTR-2:13** Concurrent requests for a given session MUST be serialized with a single writer.
- **CTR-2:14** Under Standard and High profiles, instance and session state MUST survive process restart according to the durability guarantees of the claimed profile. The Basic profile MAY relax persistence for experimentation.

<a id="file-02-envelope-interface"></a>

## Envelope Interface

**File number:** 3  
**Overview.**  
This module defines the common validation rules the controller applies to every request envelope and the catalogue of envelope types it exchanges with consoles and other parties. All control-plane interaction with consoles occurs through these envelopes.

---

### Common Validation Rules

- **CTR-3:1** The controller MUST validate every request envelope against CTR-3:2 to CTR-3:5, CTR-3:9 to CTR-3:11, and CTR-3:15.
- **CTR-3:2** The controller MUST reject any envelope whose signature fails verification against a registered console key (or other expected sender key).
- **CTR-3:3** The controller MUST reject any envelope whose timestamp falls outside the allowed skew window.
- **CTR-3:4** The controller MUST reject any envelope whose nonce has been seen before.
- **CTR-3:5** Under Standard and High profiles the controller MUST enforce strict monotonic sequence numbers per sender identity. The Basic profile MAY use weaker sequencing.
- **CTR-3:6** Unknown commands MUST be rejected; existence confers no authority.

### Envelope Catalogue (Core Types)

- **CTR-3:7** The following envelope types are recognized. Additional types may be defined by companion specifications provided they obey the common rules.

| Type | Direction | Purpose |
|---|---|---|
| `SessionStart` / `ExecutionProfile` | Console → Controller | Initiate session and supply work orders, runtimes, context |
| `SurfaceProposal` | Controller → Console | Proposed surface for validation |
| `SurfaceAcceptance` / `SurfaceRejection` | Console → Controller | Result of console validation gates |
| `Handoff` | Controller → Console | Session start credential |
| Runtime subtree intake (type name open, see CTR-O-13) | Console → Controller | Supply a console-scoped runtime subtree |
| `RuntimeInclusionDecision` | Console → Controller | Approve or deny inclusion of an already-registered runtime in a running session (see CTR-O-13) |
| `WorkOrder` / `WorkOrderUpdate` | Console → Controller | Create, extend, renew, cancel |
| `PreAuthorization` | Console → Controller | Create, change, or revoke a pre-authorization |
| `Revocation` | Console → Controller | Immediate revocation |
| `StatusQuery` / `StatusResponse` | Console ↔ Controller | State, audit, or risk information |
| `Notification` | Controller → Console | Pending decision or event |
| `CapabilityToken` | Controller → authorized party | Short-lived capability token |
| `ValidatorEvidence` | Console → Controller | Optional session-validator evidence |
| `Genesis` | Console → Controller | Console-signed anchor that locks console, Host AI, controller and gateways into one session; the genesis value MUST be 0 at handoff (see CTR-O-12) |
| `TurnReceipt` | Console → Controller | Console-signed receipt for a turn (see CTR-O-12) |

- **CTR-3:8** All of the above are ordinary envelopes subject to the common rules. No transport other than the channels defined in CTR-3:12 is permitted for control-plane actions between console and controller.

### Additional Validation Rules

- **CTR-3:9** The controller MUST reject any envelope that does not use the canonical serialization defined for its type.
- **CTR-3:10** Every envelope MUST contain a `contract_version` equal to the suite major.minor to which the sender conforms (`amk-ssot.md`, SSOT-1:3). The controller MUST reject any envelope whose `contract_version` it does not support, and MUST NOT silently downgrade.
- **CTR-3:11** Every envelope MUST contain a `ttl`. The controller MUST reject any envelope whose `ttl` has expired.

### Channels

- **CTR-3:12** The controller and a console communicate over two distinct channels. The **administrative channel** is direct, its trust is rooted in the Release Key, and it is required to initiate a session. The **session channel** carries all session-based communication through the session router; envelopes are router payloads.
- **CTR-3:13** `SessionStart` is received on the administrative channel. Once a session handle has been allocated, every session-related envelope MUST use the session channel. The assignment of the remaining envelope types to channels is not yet defined (see CTR-O-11).
- **CTR-3:14** The encapsulation of envelopes as router payloads, and the relationship between the session router and the HTSM Host AI channel, are defined by the session-router specification (see CTR-O-11).

### Nonce Length

- **CTR-3:15** Every nonce MUST be at least 128 bits.

<a id="file-03-console-identity"></a>

## Console Identity & Administration

**File number:** 4  
**Overview.**  
This module defines how consoles are identified, how their signatures are verified, and the separation between console session authority and out-of-band controller administration.

---

### Console Identity

- **CTR-4:1** Principals are consoles identified by registered keys. The controller has no operator concept.
- **CTR-4:2** No console administers the controller. An authenticated administrator does so out of band.
- **CTR-4:3** Consoles administer their own sessions through the controller.
- **CTR-4:4** The controller MUST verify console signatures on genesis, turn receipts, surface approvals, pre-authorization envelopes, and other console-originated envelopes (console key), and on surface maps (map key when a distinct map key is used).
- **CTR-4:5** Enrollment of a console’s keys with the controller is performed out of band or through a defined bootstrap procedure (currently an open item).

### Administration Separation

- **CTR-4:6** Administrative operations on the controller itself use explicit multi-phase verification and two-phase commit for destructive or irreversible actions.
- **CTR-4:7** Console-only operations (session start, surface approval, authorization, denial, revocation, runtime registration support, pre-authorization management, level changes, recovery) have no kernel-subtree node and MUST be rejected from any non-console principal.

<a id="file-04-surface-runtime"></a>

## Surface Construction, Runtime Intake & HTSM

**File number:** 5  
**Overview.**  
This module defines how the controller constructs and proposes surfaces, intakes runtime subtrees, and serves the baseline Host AI channel (HTSM). Additional channels may exist according to the kernel operating level; their definition is left to companion specifications.

---

### Runtime Subtree Intake

- **CTR-5:1** The controller receives a console-scoped runtime subtree only when a session selects the runtime or an inclusion is approved.
- **CTR-5:2** It MUST validate the subtree against kernel policy and size limits, and MUST reject any kernel-owned path, console-only operation, or minimum level lower than the risk class allows.
- **CTR-5:3** Provenance binding between a provider-signed runtime map and the console-derived subtree remains an open item; until defined, the controller treats a successfully validated subtree as authoritative for that session.

### Surface Construction

- **CTR-5:4** On session start the controller receives session information and the execution profile (work orders, scoped runtime subtrees, context assets).
- **CTR-5:5** It inspects the work orders and context, mounts the context, and builds the proposed surface from the kernel subtree, the scoped runtime subtrees, and policy-required items.
- **CTR-5:6** The controller MAY add or remove items according to policy, but on its own it MAY add only items the release policy requires.
- **CTR-5:7** It returns a `SurfaceProposal` envelope to the console. The surface is not live until the console returns a `SurfaceAcceptance` signed with the appropriate key.
- **CTR-5:8** After acceptance the controller creates the start and next endpoints and returns only a `Handoff` envelope, with genesis at 0.
- **CTR-5:9** The genesis anchor binds the approved surface.
- **CTR-5:10** Mid-session inclusion and removal produce a new surface revision; the chain and session continue and no new handoff is issued. A change to the kernel subtree requires a new session start.

### HTSM Service

- **CTR-5:11** HTSM is the baseline Host AI channel. It is not the only channel; runtimes MAY introduce other channels according to the kernel operating level.
- **CTR-5:12** The controller applies the HTSM verification order, continuation rules, fork and chain handling, console turns, and generations as defined in the HTSM companion units. This specification does not restate them.
- **CTR-5:13** A handoff is reusable until expiry only for the same session identity; an unused handoff expires. A different identity is a fork.
- **CTR-5:14** Session identity is the Host AI client fingerprint set at first use plus the delivery gateway when one was used.

<a id="file-05-work-preauth-capability"></a>

## Work Orders, Pre-Authorization, Capability & Anomaly

**File number:** 6  
**Overview.**  
This module defines the controller’s obligations for work-order enforcement, pre-authorization verification, Host AI capability testing, operating-level calculation, and anomaly-level decisions including Auto Assist.

---

### Work Orders

- **CTR-6:1** A session may hold many work orders, each with its own quota and constraints. The controller enforces them and extends, renews, or cancels them only on a console command.
- **CTR-6:2** Without a valid work order the Host AI may not engage beyond kernel requests.
- **CTR-6:3** A Host-AI-originated work order is a proposal needing console authorization unless a covering pre-authorization exists.

### Pre-Authorization Envelopes

- **CTR-6:4** The controller verifies envelope signature (console key), scope, expiry, runtime and version where relevant, per-session quota, and kernel-level cap before honoring it.
- **CTR-6:5** It honors an envelope only for the scopes it lists.
- **CTR-6:6** Duplicate of CTR-1:18. The requirement is defined only there.
- **CTR-6:7** For offline continuation, envelopes are deposited with the controller. A revocation registry is checked on every use; expiry is the backstop.
- **CTR-6:8** A runtime update to a new version voids coverage for that runtime.

### Capability Verification and Operating Level

- **CTR-6:9** The controller tests Host AI capability. Stated capability is never trusted.
- **CTR-6:10** A test runs once per Host AI profile and is repeated when something changes (model or version change, changed client signature, verification failure, Elevated anomaly, or other defined triggers).
- **CTR-6:11** A new or unverified profile starts at the baseline level.
- **CTR-6:12** Operating level is the lower of the console-allowed level and the verified capability.

### Anomaly Level and Auto Assist

- **CTR-6:13** The controller decides each session’s anomaly level: Normal, Elevated, or High.
- **CTR-6:14** The console sets, with a signed command, the allowed anomaly ceiling and the Auto Assist flag.
- **CTR-6:15** If a check-in is due and the console is unreachable, the controller lets the session continue only if Auto Assist is on, a covering envelope exists, and the anomaly level is at or below the ceiling. It may continue until the envelope expires.
- **CTR-6:16** Every such period is audited.

## Capability Tokens, Audit, Revocation & Recovery

**File number:** 7  
**Overview.**  
This module defines capability-token issuance, the append-only audit chain, revocation behaviour, multi-runtime isolation, and the recovery posture.

---

### Capability Tokens

- **CTR-7:1** The controller issues short-lived, controller-signed capability tokens bound to session, runtime, scope, nonce, and lineage.
- **CTR-7:2** Tokens for destructive or irreversible operations MUST be single-use.
- **CTR-7:3** Duplicate of CTR-1:19. The requirement is defined only there.

### Audit

- **CTR-7:4** The audit log is append-only, hash-chained, and signed by the Controller Signing Key.
- **CTR-7:5** Under Standard and High profiles, Merkle checkpoints (or equivalent integrity anchors) MUST be produced and protected according to the claimed profile.
- **CTR-7:6** Audited events include genesis, handoff use, console turns and receipts, proposals and decisions, subtree revisions, surface proposals and approvals, envelope use and revocation, capability tests, anomaly changes, Auto Assist periods, forks, and every anomaly.

### Revocation

- **CTR-7:7** Revocation commits at the controller, is audited, and halts runtimes at the next operation boundary; authority also ends at token expiry.
- **CTR-7:8** The controller keeps a revocation registry for pre-authorization envelopes.
- **CTR-7:9** Duplicate of CTR-2:13. The requirement is defined only there.

### Multi-Runtime Isolation

- **CTR-7:10** Each runtime has an isolated execution context and independent authorization scope. No inherited state or authority.

### Recovery and Availability

- **CTR-7:11** The controller fails closed during outages or integrity drops.
- **CTR-7:12** Recovery of controller identity and key material after loss or compromise is profile-dependent and remains an open item. The Basic profile may permit simpler recovery; Standard and High profiles require protocols that preserve non-exportable and hardware-backed properties.

<a id="file-07-profiles"></a>

## Operational Profiles

**File number:** 8  
**Overview.**  
This module defines the three operational profiles. An implementation MUST declare exactly one profile. Higher profiles subsume all requirements of lower profiles. Higher profiles may exclude languages or platforms that cannot meet the required isolation, key protection, durability, or audit strength.

---

### Common Rules

- **CTR-8:1** Every conformant implementation MUST declare exactly one profile: `basic`, `standard`, or `high`.
- **CTR-8:2** The declared profile MUST be discoverable through a status or capability envelope.
- **CTR-8:3** An implementation claiming `standard` MUST satisfy every Basic requirement in addition to the Standard obligations.
- **CTR-8:4** An implementation claiming `high` MUST satisfy every Basic and Standard requirement in addition to the High obligations.
- **CTR-8:5** The invariants defined in file 1 apply at every profile.

### Basic Profile

- **CTR-8:6** Software-protected keys are permitted.
- **CTR-8:7** Soft isolation is acceptable.
- **CTR-8:8** Sequencing and replay protection MAY use simplified mechanisms.
- **CTR-8:9** Minimal durable state and audit retention are acceptable.
- **CTR-8:10** Suitable for any programming language and platform that can perform the required public-key operations and maintain basic monotonic state.

### Standard Profile

- **CTR-8:11** Private keys MUST be non-exportable and protected by an OS keystore or equivalent.
- **CTR-8:12** Process or container isolation is required.
- **CTR-8:13** Full envelope sequencing, freshness, and replay protection are mandatory.
- **CTR-8:14** Durable storage with point-in-time recovery (or equivalent) and a complete signed audit chain are required.
- **CTR-8:15** Languages and platforms must support mature cryptographic libraries and process/container isolation. Implementations that cannot meet these requirements are non-conformant for the Standard profile.

### High Profile

- **CTR-8:16** Private keys MUST be protected by an HSM, secure element, or TEE and MUST NOT exist in ordinary process memory in clear form.
- **CTR-8:17** Strong isolation (TEE or equivalent hardware security domain) is required.
- **CTR-8:18** Measured boot / remote attestation SHOULD be supported.
- **CTR-8:19** The audit trail MUST be protected against tampering (hardware-backed or equivalently strong integrity protection).
- **CTR-8:20** Side-channel resistance and high-assurance coding practices are expected for security-critical paths.
- **CTR-8:21** Languages and platforms that cannot provide HSM/TEE support, measured boot, or the required isolation and audit strength are excluded from the High profile.

### Profile Summary Table

| Requirement | Basic | Standard | High |
|---|---|---|---|
| Non-exportable keys | SHOULD | MUST | MUST |
| OS keystore / equivalent | MAY | MUST | MUST |
| HSM / TEE / secure element | — | MAY | MUST |
| Keys never in clear process memory | — | SHOULD | MUST |
| Process / container isolation | MAY | MUST | MUST |
| TEE-level isolation | — | — | MUST |
| Full sequencing + replay protection | MAY (simplified) | MUST | MUST |
| Durable state + signed audit | Minimal | Full | Hardware-protected |
| Remote attestation support | — | — | SHOULD |
| Language / platform exclusion | None (basic crypto) | Must support isolation + mature crypto | Must support HSM/TEE + measured environment |

### Peer Profile Rule

- **CTR-8:22** The controller MUST NOT accept a peer that declares a lower profile than its own unless the administrator has explicitly allowed it, and that allowance MUST be audited.

## Controller Key Hierarchy

**File number:** 10  
**Overview.**  
This module defines the key roles held or verified by the controller and the trust relationships that anchor them. Key protection strength per profile is defined in file 8 and is not repeated here. Items not yet decided are listed in file 9 (see CTR-O-16).

---

### Key Roles

- **CTR-10:1** The controller distinguishes three key roles: the Release Key, the Controller Signing Key, and the Token Signing Key.
- **CTR-10:2** A key MUST NOT serve more than one role.

### Release Key

- **CTR-10:3** The Release Key is used to sign the Release Manifest. The controller holds and uses only its verification key(s). The private key MUST NOT be present on the controller.
- **CTR-10:4** The controller MUST verify the Release Manifest against the Release Key before accepting any connection (CTR-2:1, CTR-2:6).
- **CTR-10:5** Trust in the administrative channel (CTR-3:12) is rooted in the Release Key.

### Controller Signing Key

- **CTR-10:6** The Controller Signing Key signs controller-originated envelopes (including `SurfaceProposal`), audit entries, and checkpoints (CTR-1:3, CTR-7:4).
- **CTR-10:7** The Controller Signing Key MUST NOT sign capability tokens.

### Token Signing Key

- **CTR-10:8** The Token Signing Key signs capability tokens only (CTR-7:1).
- **CTR-10:9** A compromise of the Token Signing Key MUST NOT enable forging of envelopes, audit entries or checkpoints.

### Console Pins

- **CTR-10:10** A console build pins the Release Key fingerprint(s), the list of controller URLs, and the list of Authority URLs (CNS-2:12). The controller is administered out of band and consoles are principals only (CTR-4:2).

### Migration Notes

- All references to Cloudflare (or any specific platform or vendor) have been removed.
- The specification is language- and platform-agnostic. Higher profiles may exclude languages or platforms that cannot meet the required isolation, key protection, or audit strength.
- All UI/UX and presentation material has been removed.
- Control-plane interaction with consoles is expressed solely through envelopes.
- Three operational profiles (Basic / Standard / High) are defined in file 8.
- Reference IDs follow the single scheme `CTR-<file>:<rule>`.
- `RuntimeRegistration` and `ClarificationAnswer` were removed from the catalogue. `Genesis` and `TurnReceipt` were added. Common envelope validation now includes `contract_version` and `ttl` (CTR-3:10, CTR-3:11).
- File 10 (`08-keys.md`) was added. File numbers are stable identifiers and need not follow file-name order.
- Cross-spec open items are indexed in `specs/core/OPEN-ITEMS.md`.
