## Holistic System Overview

A runtime extends the kernel with capability. The kernel itself (the core OS/10 capabilities scaffolded by the kernel subtree) has no runtime. Everything beyond it, including the bundled system package `amk-core`, arrives as a runtime package.

The amk-runtime component is the single defined authority over **runtime packages**: what a package is, who signed it, whether it conforms to the protocol standards, and when and how its code is brought into execution. It is also the **loader**: the only means by which package code is placed into an execution context for a session.

It is deliberately **not** an authority over authorization or enforcement. The human operator, acting through the console, alone decides which packages are registered and which are included in a session. The controller alone enforces, issues capability tokens and holds state. The Attestation Authority alone issues role attestations. amk-runtime verifies and loads what those parties have already decided; it never decides for them.

Every runtime package, system packages included, must be downloaded and registered by the operator through the console, and its inclusion in a session must be authorized through the console. A console-signed pre-authorization may cover that inclusion where the console spec allows it (see RTM-O-04).

The specification is language-agnostic. Platform-specific loader implementations (for example sandboxed isolates on an edge platform) are described in companion implementation profiles, not here.

Three operational profiles (Basic, Standard, High) govern isolation, verification strength, and audit. Higher profiles subsume all requirements of lower profiles.

This document is an index. Normative requirements live in the module files listed below.

## Foundations — Terms, Role, Authority Limits, Trust & Invariants

**File number:** 1  
**Overview.**  
This module defines the core terminology, the role of amk-runtime as package authority and loader, the explicit limits of that authority, the trust boundary, and the absolute invariants. All subsequent modules presuppose these definitions.

---

### Terms

| Term | Meaning |
|---|---|
| Runtime | A package-delivered unit of capability that extends the kernel. It has no authority of its own. |
| Runtime package | The signed, versioned artefact that delivers a runtime (file 2). |
| Package class | `system` (shipped with a release, Release-signed) or `third-party` (publisher-signed). |
| Package manifest | The signed description of a package: identity, version, class, contract version, declarations. |
| Runtime map | The package's full proposed surface map: every node the runtime could contribute to the Host Traversal Surface Map (HTSM). |
| Runtime subtree | The console-scoped derivation of a runtime map for a given operator, runtime settings and profile. |
| In-band API | The interface through which the controller invokes a loaded runtime (file 3). |
| UI manifest | A zip of declarative UI definitions the console renders on the runtime's behalf. |
| Loader | The component that verifies a package and places its code into an isolated execution context. |
| Package authority | The role of establishing package identity, provenance and conformance. |
| Publisher | The party whose key signs a third-party package. |
| Registration | The console-side act of installing a package after verification and operator confirmation. |
| Inclusion | The operator-authorized addition of a registered runtime to a session. |
| Retire | To end in-flight work for a runtime with a defined error code before removal. |
| Kernel subtree | The part of the surface scaffolded by the kernel with no runtime. |
| Surface | The Host AI traversal surface (HTSM) built for a session. |
| Core runtime | A runtime available in every AMK release. |
| `amk-core` | The bundled group of core runtime capabilities, loaded first (file 7). |

---

### Role

- **RTM-1:1** amk-runtime is the sole defined authority over the identity, provenance, conformance and lifecycle of runtime packages, including system packages.
- **RTM-1:2** amk-runtime is the loader: package code MUST enter execution only through the loader.
- **RTM-1:3** A runtime is a unit of capability that extends the kernel. It holds no authority of its own and cannot widen any authority granted to it.

### Authority Limits

- **RTM-1:4** amk-runtime does not authorize. Authority to register a package and to include it in a session rests solely with the operator, expressed through console-signed envelopes.
- **RTM-1:5** amk-runtime does not enforce. Enforcement, capability-token issuance and session state belong to the controller.
- **RTM-1:6** amk-runtime does not issue role attestations. That belongs to the Attestation Authority.
- **RTM-1:7** System packages, including `amk-core`, have the same authority as any other runtime. Their class affects provenance and load order only.

### Trust Boundary

- **RTM-1:8** Trusted: the Release Key (for system packages and the Release Manifest), console keys (for operator intent only), and the loader's own verification logic (subject to the claimed profile).
- **RTM-1:9** Trusted only for what they sign, and only after operator registration: publishers of third-party packages.
- **RTM-1:10** Untrusted: runtime code, package repositories and transports, the Host AI, and unauthenticated parties.
- **RTM-1:11** Repositories are untrusted transport. Authority derives from signatures and operator registration, never from where a package was obtained.

### Invariants

- **RTM-1:12** No implicit authority. A package is never loaded, registered or included because of its presence, its class, its name or its repository.
- **RTM-1:13** Package code is never executed before its signature, hash and contract version have been verified.
- **RTM-1:14** A package is never loaded into a session without a console-signed inclusion decision (or a covering console-signed pre-authorization, see RTM-O-04).
- **RTM-1:15** A runtime never receives console keys, operator credentials, controller keys or another runtime's state.
- **RTM-1:16** A runtime MUST NOT weaken or alter kernel boundaries (CTR-1:12).
- **RTM-1:17** Any verification failure fails closed and is audited.
- **RTM-1:18** No runtime provides an external user interface. Every runtime UI is administered by the console.
- **RTM-1:19** No silent downgrades of contract, package or runtime versions.

**RTM-1:20** An implementation that violates any invariant listed above is non-conformant.

## Package Format — Structure, Manifest, Identity, Versioning & Signatures

**File number:** 2  
**Overview.**  
This module defines what a runtime package contains and how it is identified, versioned and signed. It is the only place package structure is defined. Concrete serialization and hash algorithms are deferred to the shared envelope serialization decision (see RTM-O-13).

---

### Package Contents

- **RTM-2:1** A runtime package MUST contain exactly one manifest and the following content parts:
  - **Prompts:** the scaffolding text delivered to the Host AI through the runtime's subtree.
  - **In-band API descriptor:** the operations the runtime implements (file 3) and its executable code.
  - **Runtime map:** the full proposed surface map.
  - **UI manifest:** a zip of declarative UI definitions. It MUST provide at least an "about" view and a "settings" view.
  - **Settings schema:** the settings the operator may change, and which settings influence the subtree.
- **RTM-2:2** A package MUST NOT contain a user interface that runs outside the console's rendering of the UI manifest.
- **RTM-2:3** A package MUST NOT contain keys, credentials or operator-specific data.

### Manifest

- **RTM-2:4** The manifest MUST declare:
  - `package_id` and `version`,
  - `class` (`system` or `third-party`),
  - `publisher_id` (third-party) or the Release identity (system),
  - `contract_version` (the runtime contract version it implements),
  - `min_kernel_level` and the highest risk class of any operation it exposes (see CTR-O-13),
  - declared channels beyond HTSM, if any,
  - declared egress destinations, if any,
  - resource requests (CPU time, memory, size),
  - a digest of every content part.
- **RTM-2:5** Anything not declared in the manifest MUST be treated as not permitted.
- **RTM-2:6** The manifest MUST be self-consistent: every content part present is digested, and every digest refers to a present part.
- **RTM-2:7** A package MUST NOT declare a dependency on another runtime's authority or state. Runtime-to-runtime dependencies are not supported in this version (see RTM-O-07).

### Identity and Versioning

- **RTM-2:8** A package is identified by the pair (`package_id`, `version`) and by its package hash.
- **RTM-2:9** The package hash is computed over the canonical manifest, which includes the digests of every content part.
- **RTM-2:10** A published (`package_id`, `version`) is immutable. Any change to any content part MUST produce a new version and a new package hash.
- **RTM-2:11** `package_id` MUST be unique per publisher. The globally unique identity of a package is (`publisher_id`, `package_id`).

### Signatures

- **RTM-2:12** Every package MUST carry a signature over the canonical manifest.
- **RTM-2:13** Third-party packages MUST be signed by the publisher's key.
- **RTM-2:14** System packages MUST be signed by the Release Key and MUST be listed in the Release Manifest by identity and package hash (file 7).
- **RTM-2:15** The signature algorithm MUST be identifiable from the package or from published publisher metadata. Verifiers MUST reject an unknown or unsupported algorithm.
- **RTM-2:16** A package whose signature, manifest consistency or content digests fail verification MUST be rejected.

### Update Metadata

- **RTM-2:17** A package MAY carry update metadata identifying the publisher's update channel. Update status (current, advisory, mandatory, withdrawn) is governed by file 6 and is not part of the signed package hash.

## Runtime Contract — In-Band API, Runtime Map, Channels, UI & Errors

**File number:** 3  
**Overview.**  
This module defines exactly what a runtime is obliged to provide and what it may and may not do. The contract is the same for every runtime. Wire formats and transports are deferred (see RTM-O-12).

---

### Contract Version

- **RTM-3:1** The runtime contract carries a version. A runtime declares the version it implements in its manifest.
- **RTM-3:2** The loader MUST reject a package whose contract version it does not support. It MUST NOT silently downgrade (RTM-1:19).

### In-Band API

- **RTM-3:3** A runtime MUST implement the following operations, invoked only by the controller through the loader:
  - **Describe:** return the runtime's declared identity, version, and operations.
  - **Initialize:** prepare the runtime in a fresh execution context for one session.
  - **Include:** attach the runtime to a session after an inclusion decision.
  - **Invoke:** perform one operation requested through the surface, under a capability token.
  - **Retire:** stop accepting new work and end in-flight work with the defined retirement error.
  - **Detach:** release all session resources.
- **RTM-3:4** Every `Invoke` carries the session handle and the controller-issued capability token (CTR-7:1). The runtime MUST verify the token and MUST refuse the operation if verification fails.
- **RTM-3:5** A runtime MUST NOT be invoked by any party other than the controller through the loader.
- **RTM-3:6** A runtime MUST NOT receive a console key, an operator credential, or a controller key at any point.
- **RTM-3:7** The Host AI never calls the in-band API. It reaches a runtime only through the surface.

### Runtime Map

- **RTM-3:8** The runtime map declares the full proposed surface the runtime could contribute. Each node MUST state its minimum kernel level, its risk class, and the settings, if any, that control its visibility.
- **RTM-3:9** A runtime map MUST NOT contain a kernel-owned path or a console-only operation (CTR-5:2, CTR-4:7).
- **RTM-3:10** The console derives the runtime subtree from the runtime map according to the operator's runtime settings or runtime profile. A subtree MUST be a subset of the map. A runtime MUST NOT expand its own subtree.

### Channels

- **RTM-3:11** A runtime reaches the Host AI only through HTSM, the baseline channel.
- **RTM-3:12** A runtime MAY use an additional channel only if the channel is declared in its manifest, is permitted at the session's kernel operating level, and was approved at inclusion (see CTR-O-06).
- **RTM-3:13** A runtime MUST NOT communicate with the console directly. The console reaches a runtime only through the controller.

### User Interface

- **RTM-3:14** A runtime presents UI to the operator only through its UI manifest, rendered by the console.
- **RTM-3:15** The operator decides which settings reach the Host AI. A runtime MUST NOT transmit a setting to the Host AI that the operator has not allowed in its subtree.
- **RTM-3:16** A runtime MUST NOT open an interface to the operator that bypasses the console.

### Prompts

- **RTM-3:17** Runtime prompts are scaffolding data delivered through the runtime's subtree. They carry no authority.
- **RTM-3:18** The prompts of a system package that scaffolds through the kernel subtree are governed by file 7.

### Errors and Failure Scope

- **RTM-3:19** A runtime MUST report failures using standard error codes defined in the contracts layer (see RTM-O-12).
- **RTM-3:20** The retirement error MUST be used for work in flight when a runtime is removed or retired.
- **RTM-3:21** A runtime failure is scoped to that runtime and that session (CTR-2:7). It MUST NOT halt another runtime or session.

### State

- **RTM-3:22** Runtime state is isolated per runtime and per session. A runtime MUST NOT inherit state or authority from another runtime or session (CTR-7:10).
- **RTM-3:23** Any state a runtime keeps beyond a session is not defined in this version (see RTM-O-06).

## Lifecycle — Registration, Loading, Inclusion, Removal & Update

**File number:** 4  
**Overview.**  
This module defines the lifecycle of a runtime package from arrival to removal and states exactly who decides at each step. Envelope names are placeholders pending the cross-spec envelope decisions (see RTM-O-02).

---

### States

- **RTM-4:1** A runtime package moves through these states: `ARRIVED → VERIFIED → REGISTERED → LOADED → INCLUDED → RETIRING → REMOVED`. A package may also be `REJECTED` (verification or operator rejection), `WITHDRAWN` (file 6) or `SUSPENDED` (loader fault).
- **RTM-4:2** State is scoped. `ARRIVED`, `VERIFIED` and `REGISTERED` are console-local per operator. `LOADED`, `INCLUDED` and `RETIRING` are scoped to a session and a runtime.

### Registration (install)

- **RTM-4:3** A package MAY arrive by file, link, in-app repository, QR code or paste. The arrival method confers no trust (RTM-1:11).
- **RTM-4:4** Registration is performed by the console. The console MAY reject the package at any failed step.
- **RTM-4:5** Before registering, the console MUST verify the manifest consistency, content digests, signature, contract version and conformance (file 6), and MUST require the operator's fresh confirmation of the package identity and, for third-party packages, the publisher.
- **RTM-4:6** Fresh confirmation for registration is required under every profile (see RTM-O-20).
- **RTM-4:7** System packages are registered in the same way as any other package (file 7).
- **RTM-4:8** Registration is console-local. The console records the package identity and package hash it accepted and uses that record for every later inclusion.

### Session Start With A Runtime

- **RTM-4:9** When a session selects a runtime, the console supplies the controller with the scoped runtime subtree and a package reference (identity and package hash) in a console-signed envelope (see RTM-O-02).
- **RTM-4:10** The loader MUST confirm that the package it is about to load matches the package hash in the console-signed reference. A mismatch MUST abort the load.
- **RTM-4:11** The loader then verifies the package (file 5), loads it, and initializes it. The controller builds the surface as defined in CTR-5:4 to 5:9.
- **RTM-4:12** The runtime is not live until the console has returned a `SurfaceAcceptance` and the handoff has been issued.

### Mid-Session Inclusion

- **RTM-4:13** Inclusion may be requested by the Host AI through the surface or by the operator.
- **RTM-4:14** The console decides inclusion. Where no covering pre-authorization exists, the operator must authorize it (see RTM-O-04).
- **RTM-4:15** After an inclusion decision, the loader loads and initializes the package. The controller produces a new surface revision. No new handoff is issued (CTR-5:10).
- **RTM-4:16** A change to the kernel subtree requires a new session start and is never a mid-session inclusion.

### Removal and Retirement

- **RTM-4:17** The operator may remove a runtime during a session through a console-signed revocation.
- **RTM-4:18** On removal, the loader MUST stop the runtime at the next operation boundary, MUST end in-flight work with the retirement error (RTM-3:20), and MUST release all resources.
- **RTM-4:19** Removal produces a new surface revision. Capability tokens for the runtime end at expiry (CTR-7:7).

### Update

- **RTM-4:20** A new version of a package is a different package (RTM-2:10). It MUST be registered by the operator before it can be included.
- **RTM-4:21** A runtime update to a new version voids pre-authorization coverage for that runtime (CTR-6:8).
- **RTM-4:22** The loader MUST NOT load a version whose status is `WITHDRAWN`.
- **RTM-4:23** A `mandatory` update flag (file 6) never installs a package automatically. It only blocks inclusion of the superseded version after its effective time.

### Operator Authorization Rule

- **RTM-4:24** Every runtime package, system or third-party, requires operator registration through the console and console-authorized inclusion in every session. A covering console-signed pre-authorization MAY authorize that inclusion where the console specification permits (see RTM-O-04).

## Loader — Verification, Load Order, Isolation & Limits

**File number:** 5  
**Overview.**  
This module defines the obligations of the loader: what it verifies before any code runs, in what order packages load, how each runtime is isolated, and what limits apply. The loader is platform-agnostic here; implementation profiles describe concrete mechanisms.

---

### Placement

- **RTM-5:1** The loader is delivered as part of the controller release and is bound to the controller's trust root. Its identity and hash MUST be pinned in the Release Manifest (see RTM-O-01).
- **RTM-5:2** The loader MUST run behind an isolation boundary from the controller's enforcement logic. A fault or compromise inside a loaded runtime MUST NOT reach controller keys or enforcement state.
- **RTM-5:3** The loader MUST NOT hold console keys or operator credentials.

### Verification Before Load

- **RTM-5:4** Before executing any package code, the loader MUST verify, in this order:
  - the package hash matches the console-signed reference (RTM-4:10),
  - the manifest is self-consistent and every content digest matches,
  - the signature verifies against the correct key for the package class (Release Key for system, publisher key for third-party),
  - the contract version is supported,
  - the package is not `WITHDRAWN` or revoked (file 6),
  - the manifest's declared level, channels, egress and resources are acceptable under the session's kernel operating level and the loader's limits.
- **RTM-5:5** If any check fails, the loader MUST NOT execute the package, MUST report a standard error code to the controller, and MUST audit the failure.
- **RTM-5:6** The loader MUST NOT cache or reuse a package under any key other than its package hash. A cached copy MUST be re-verified on every load.

### Load Order

- **RTM-5:7** System packages load first, in the deterministic order fixed by the Release Manifest (file 7).
- **RTM-5:8** Third-party packages load after system packages, in the order selected by the console for the session.
- **RTM-5:9** Load order MUST NOT confer authority. A runtime loaded earlier has no privilege over one loaded later.

### Isolation

- **RTM-5:10** Each runtime executes in its own execution context, separate for each session. Contexts share no memory, state or authority (RTM-3:22, CTR-7:10).
- **RTM-5:11** Network egress from a runtime is denied by default. Only egress declared in the manifest and approved at inclusion is allowed (profile-dependent, file 8).
- **RTM-5:12** A runtime MUST NOT access controller storage, console storage, keys, or another runtime's context.
- **RTM-5:13** The loader mediates every call into and out of a runtime. A runtime has no direct handle to any other component.

### Resource Limits

- **RTM-5:14** The loader MUST enforce limits on CPU time, memory, package size, call duration and outbound calls for every runtime.
- **RTM-5:15** Limit values come from the defaults manifest (`DV-RTM-nn`, see file 9) and MAY be tightened per session by the controller. They MUST NOT be raised by a runtime.
- **RTM-5:16** A runtime that exceeds a limit MUST be stopped, and the event reported to the controller and audited.

### Failure Handling

- **RTM-5:17** The loader fails closed. A faulted runtime is moved to `SUSPENDED` for that session and its in-flight work ends with an error code.
- **RTM-5:18** A fault in one runtime MUST NOT halt another runtime or another session (CTR-2:7).

### Audit

- **RTM-5:19** The loader MUST emit audit events to the controller for: package verification results, load, include, remove, retire, limit breaches, faults, and rejected packages.
- **RTM-5:20** The loader MUST NOT write to the controller's audit chain directly. The controller records and signs audit entries (CTR-7:4).

## Package Authority — Provenance, Publishers, Repositories, Update Flags & Revocation

**File number:** 6  
**Overview.**  
This module defines how package identity and trust are established: who may sign, how the operator's trust decisions are recorded, how repositories are treated, how update status is published, and how a package is withdrawn.

---

### Roles

- **RTM-6:1** The Release Authority signs system packages with the Release Key.
- **RTM-6:2** A publisher signs third-party packages with the publisher's key.
- **RTM-6:3** The operator alone decides which publishers and packages to trust, through the console.

### Provenance

- **RTM-6:4** A package is accepted only if its signature verifies and the operator has registered it (RTM-4:4, RTM-4:5).
- **RTM-6:5** The console MUST record, at registration, the publisher identity, the publisher key and the package hash the operator accepted.
- **RTM-6:6** A change of publisher key for an already-registered publisher MUST be treated as a new publisher and require fresh operator confirmation.
- **RTM-6:7** System packages are accepted only if listed in the Release Manifest with a matching package hash (file 7).

### Repositories

- **RTM-6:8** "Public" and "private" describe how a package is distributed through an in-app repository. They do not refer to source-code visibility.
- **RTM-6:9** A public repository is available to every operator of the application.
- **RTM-6:10** A private repository is available either to a single operator or shared among a defined set of operators. Only the operator holds installation keys.
- **RTM-6:11** A repository is untrusted transport (RTM-1:11). Listing in a repository confers no authority.
- **RTM-6:12** Repository protocol details are not defined in this version (see RTM-O-15).

### Conformance

- **RTM-6:13** A package MUST meet the protocol standards defined by a versioned conformance rule set. The rule set is not yet defined (see RTM-O-08).
- **RTM-6:14** Both the console (at registration) and the loader (at load) MUST apply the conformance rule set. A failure at either point rejects the package.

### Update Status

- **RTM-6:15** Each (`package_id`, publisher) MAY have an update status published in an update profile database with one of these values: `current`, `advisory`, `mandatory`, `withdrawn`.
- **RTM-6:16** `advisory` means a newer version is available and recommended. `mandatory` means the console MUST block inclusion of the superseded version after the effective time. `withdrawn` means the version MUST NOT be loaded.
- **RTM-6:17** Update status is a signed statement by the publisher (third-party) or the Release Authority (system). Unsigned or wrongly signed status MUST be ignored.
- **RTM-6:18** The location, signer, and schema of the update profile database are not yet defined (see RTM-O-09).

### Package Revocation

- **RTM-6:19** A publisher or the Release Authority MAY withdraw a package version by publishing a signed withdrawal statement.
- **RTM-6:20** The console MUST surface a withdrawal to the operator. The loader MUST refuse to load a withdrawn version (RTM-4:22).
- **RTM-6:21** Package withdrawal is separate from revocation of role attestations (`ATA-04`) and of pre-authorizations (`CNS-5:10`).
- **RTM-6:22** Withdrawing a package does not by itself end a running session. The operator ends it through the console.

<a id="file-06-system-packages"></a>

## System Packages and amk-core

**File number:** 7  
**Overview.**  
This module defines the system package class and the rules for `amk-core`. System packages differ from third-party packages in provenance and load order, never in authority. The content of `amk-core` itself (its modules and tests) belongs to its own specification.

---

### System Package Class

- **RTM-7:1** A system package is shipped with an AMK release and signed by the Release Key.
- **RTM-7:2** Every system package MUST be listed in the Release Manifest by `package_id`, version and package hash, in the deterministic load order.
- **RTM-7:3** A system package follows the same contract (file 3), the same lifecycle (file 4) and the same loader obligations (file 5) as any other runtime.
- **RTM-7:4** A system package MUST NOT be granted any authority, privilege, risk class or level beyond those it declares and the controller and console grant. Class is not authority (RTM-1:7).
- **RTM-7:5** Every system package requires operator registration and console-authorized inclusion, exactly like a third-party package (RTM-4:24). Registration of the system packages is part of the console's first-run wizard.
- **RTM-7:6** Because system packages ship with a release, their versions change only with a new Release Manifest.

### Core Runtimes

- **RTM-7:7** A core runtime is a runtime available in every AMK release. A core runtime is a system package.
- **RTM-7:8** At least one core runtime MUST exist so that the system can be exercised end to end.
- **RTM-7:9** A runtime that is not part of every release, for example StepWise, is not a core runtime and is a third-party package.

### amk-core

- **RTM-7:10** `amk-core` is the bundled group of core runtime capabilities, loaded first (RTM-5:7).
- **RTM-7:11** `amk-core` is a system runtime. Its prompts scaffold through the kernel subtree, not through the controller. Authority rests with the console.
- **RTM-7:12** Where a system package scaffolds through the kernel subtree, its content is bound to the release: its package hash is covered by the Release Manifest, and changing it requires a new release.
- **RTM-7:13** Inclusion or removal of a system package that scaffolds through the kernel subtree is a change to the kernel subtree. It therefore takes effect only at a new session start and is never a mid-session inclusion (RTM-4:16, CTR-5:10). This is a draft position (see RTM-O-05).
- **RTM-7:14** The first tests of `amk-core` MUST exercise the kernel separation boundaries: a session with and without a runtime, and a runtime added and removed during an active session.

### Candidate First Module (non-normative)

- A host clarification module: a quiz-style UI shown to the operator for quick answers the Host AI needs, answered through the console (see `ClarificationAnswer`, CNS-3). Its definition belongs to the `amk-core` specification (see RTM-O-18).

<a id="file-07-profiles"></a>

## Operational Profiles

**File number:** 8  
**Overview.**  
This module defines the three operational profiles—Basic, Standard, and High—that govern verification strength, isolation and audit for the loader and package authority. An implementation MUST declare exactly one profile. Higher profiles subsume all requirements of lower profiles.

---

### Common Rules

- **RTM-8:1** Every conformant implementation MUST declare exactly one profile: `basic`, `standard`, or `high`.
- **RTM-8:2** The declared profile MUST be discoverable through a status or capability envelope.
- **RTM-8:3** An implementation claiming `standard` MUST satisfy every Basic requirement in addition to the Standard obligations.
- **RTM-8:4** An implementation claiming `high` MUST satisfy every Basic and Standard requirement in addition to the High obligations.
- **RTM-8:5** The invariants in file 1 apply at every profile. Signature, hash and contract-version verification are mandatory at every profile.

---

### Basic Profile

**Target:** Hobbyists, educational use, rapid prototypes.

- **RTM-8:6** Software-protected verification keys are permitted.
- **RTM-8:7** Soft isolation between runtime contexts is acceptable.
- **RTM-8:8** Egress control MAY be advisory, but undeclared egress MUST still be refused.
- **RTM-8:9** Resource limits MUST be enforced, with simplified mechanisms permitted.
- **RTM-8:10** Minimal audit retention is acceptable.

### Standard Profile

**Target:** Production services and professional deployments.

- **RTM-8:11** Verification keys MUST be non-exportable and protected by an OS keystore or equivalent.
- **RTM-8:12** Each runtime MUST run in its own process, container or isolate with no shared memory.
- **RTM-8:13** Egress MUST be denied by default and enforced by the platform, not by the runtime.
- **RTM-8:14** A complete signed audit of verification, load, include, remove, fault and rejection events MUST be maintained.
- **RTM-8:15** Cached packages MUST be stored keyed by package hash with integrity protection.

### High Profile

**Target:** Enterprise, regulated and high-assurance environments.

- **RTM-8:16** Verification keys MUST be protected by an HSM, secure element or TEE.
- **RTM-8:17** Runtime contexts MUST be isolated by a hardware-backed security domain or equivalent.
- **RTM-8:18** Measured load and remote attestation of the loader SHOULD be supported.
- **RTM-8:19** The audit trail MUST be protected against tampering by hardware-backed or equivalently strong integrity protection.
- **RTM-8:20** System packages SHOULD be reproducibly built so their package hash can be independently reproduced.

---

### Profile Summary Table

| Requirement | Basic | Standard | High |
|---|---|---|---|
| Signature, hash, contract-version verification | MUST | MUST | MUST |
| Verification key protection | Software | OS keystore | HSM / TEE |
| Runtime isolation | Soft | Process / container / isolate | Hardware-backed |
| Undeclared egress refused | MUST | MUST | MUST |
| Egress denied by default, platform-enforced | MAY (advisory) | MUST | MUST |
| Resource limits | MUST (simplified) | MUST | MUST |
| Signed lifecycle audit | Minimal | Full | Hardware-protected |
| Package cache keyed by hash with integrity | SHOULD | MUST | MUST |
| Loader attestation | — | — | SHOULD |
| Reproducible system packages | — | — | SHOULD |
